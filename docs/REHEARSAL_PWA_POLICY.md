# 1. 서비스 목적

기존 밴드 동아리 합주 시간 조율 과정은 다음과 같은 문제가 있다.

- 특정 시각에 카카오톡 단체방에서 팀장들이 선착순으로 합주 시간을 잡음
- 서기가 카카오톡 메시지를 일일이 확인해 시간표로 옮김
- 일정 수정/취소 시 서기가 다시 가능한 시간을 확인하고 공지함
- 팀끼리 일정을 바꾸고 싶어도 중간 조정자가 필요함
- 예약 오픈 순간 여러 팀장이 동시에 요청할 경우 정확한 선착순 처리가 필요함

본 서비스는 이를 다음과 같이 해결한다.

> **밴드 동아리 내부에서 합주 시간 예약, 일정 수정·취소·교환, 공지, 예약 정책, 관리자 강제 조정을 하나의 PWA에서 처리한다.**

# 3. 서비스 범위 원칙

## 3.1 단일 동아리 기준

MVP는 **현재 동아리 하나**를 기준으로 개발한다.

- 여러 대학 동아리가 가입하는 SaaS 구조는 MVP에서 제외
- 필요 시 추후 멀티 동아리 구조로 확장 가능하도록 고려

## 3.2 공연(Event)은 핵심 도메인에서 제외

합주 예약은 특정 축제나 공연에 종속되지 않는다.

```text
동아리
├─ 회원
├─ 곡/팀
├─ 합주 일정
├─ 공지
└─ 예약 운영
```

공연 기능이 필요해질 경우 추후 부가 기능으로 추가한다.

# 4. 사용자 권한

전역 권한은 다음 세 단계로 구분한다.

```text
MEMBER
ADMIN
SUPER_ADMIN
```

---

## 4.1 MEMBER

일반 부원.

가능한 기능:

- 로그인 / 로그아웃
- 공지 조회
- 전체 합주 일정 조회
- 내 합주 일정 조회
- 본인이 참여하는 곡 조회
- 알림 조회
- 개인 알림 설정
- 본인 회원 탈퇴

---

## 4.2 곡 팀장

팀장은 전역 Role이 아니다.

각 곡에 **정확히 1명**의 팀장을 둔다.

예:

```text
아지랑이
- 장OO: 기타 / 팀장
- 김OO: 보컬
- 이OO: 베이스
- 박OO: 드럼
```

같은 사용자가:

```text
아지랑이       → 팀장
Silhouette     → 일반 참여자
한낮           → 일반 참여자
```

일 수 있다.

팀장 추가 권한:

- 자신이 팀장인 팀의 합주 예약
- 예약 이동
- 예약 시간 연장 / 단축
- 예약 취소
- 다른 팀에 일정 교환 요청
- 자신의 팀에 들어온 교환 요청 수락 / 거절

공동 팀장은 MVP에서 허용하지 않는다.

---

## 4.3 ADMIN

관리자.

가능한 기능:

- 가입 신청 승인 / 거절
- 회원 관리
- 일반 회원 삭제
- 곡 생성 / 수정 / 보관
- 곡 참여자 구성
- 참여자 세션 입력
- 팀장 지정 / 변경
- 공지 작성 / 수정 / 삭제
- 예약 정책 관리
- 초대코드 재발급
- 날짜별 동아리방 운영시간 설정 / 기본값 복원
- 동아리방 사용 불가 시간 관리
- 전체 일정 관리
- 관리자 강제 일정 생성
- 관리자 강제 일정 이동
- 관리자 앞쪽 / 뒤쪽 강제 연장
- 관리자 앞쪽 / 뒤쪽 강제 단축
- 관리자 강제 일정 취소
- 관리자 직접 일정 교환
- 관리자 작업 이력 조회

---
## 4.4 SUPER_ADMIN

최초 시스템 소유자.

### 생성

서버 최초 실행 시 환경변수로 1개의 SUPER_ADMIN 계정을 생성한다.

예정 환경변수:

```text
INITIAL_ADMIN_LOGIN_ID
INITIAL_ADMIN_PASSWORD
INITIAL_ADMIN_NAME
```

비밀번호는 DB에 평문 저장하지 않고 안전한 해시로 저장한다.

### 특수 정책

- SUPER_ADMIN은 삭제 불가
- SUPER_ADMIN은 탈퇴 불가
- SUPER_ADMIN 권한 해제 불가
- SUPER_ADMIN → ADMIN 강등 불가
- SUPER_ADMIN → MEMBER 강등 불가
- 다른 회원을 ADMIN으로 승격 가능
- 기존 ADMIN을 MEMBER로 강등 가능

SUPER_ADMIN은 정확히 1명을 유지한다.

# 5. 회원가입 및 인증 정책

## 5.1 회원가입 정보

회원가입 시 다음 정보만 받는다.

```text
초대코드
로그인 아이디
비밀번호
이름
```

이메일은 받지 않는다.

---

## 5.2 회원가입 흐름

```text
회원가입
→ 초대코드 검증
→ 아이디 / 비밀번호 / 이름 입력
→ 가입 신청
→ 관리자 승인 대기
→ ADMIN 또는 SUPER_ADMIN 승인
→ 로그인 가능
```

승인 전 사용자는 서비스 주요 기능에 접근할 수 없다.

---

## 5.3 가입 거절

관리자가 가입 신청을 거절해도 동일 아이디로 다시 가입 신청할 수 있다.

```text
가입 신청
→ 거절
→ 동일 아이디 재신청 가능
```

과거 거절 이력은 관리자 기록에 남긴다.

---

## 5.4 초대코드

- ADMIN / SUPER_ADMIN 재발급 가능
- 별도 만료일 없음
- 새 코드 재발급 시 기존 코드는 즉시 폐기
- 초대코드를 알고 있어도 관리자 승인이 있어야 최종 가입 가능

---

## 5.5 로그인 유지 방식

JWT 기반 인증을 사용한다.

```text
Access Token
Refresh Token
```

저장 방식:

```text
HttpOnly + Secure Cookie
```

원칙:

- 토큰을 `localStorage`에 저장하지 않음
- 프론트 JavaScript에서 인증 쿠키를 직접 읽지 않음
- 브라우저/PWA가 API 요청 시 쿠키 자동 전달
- API 호출 시 필요하면 `credentials: "include"` 사용

---

## 5.6 비밀번호 분실

이메일 복구 기능은 MVP에서 제공하지 않는다.

비밀번호 분실 시 관리자에게 요청하여 초기화한다.

---

# 6. 회원 삭제 / 탈퇴 정책

회원 삭제는 물리 삭제하지 않는다.

## 6.1 회원 본인 탈퇴

MEMBER / ADMIN은 본인 계정을 탈퇴할 수 있다.

탈퇴 시:

```text
현재 비밀번호 재확인
→ 최종 확인
→ 탈퇴 처리
```

SUPER_ADMIN은 탈퇴할 수 없다.

---

## 6.2 관리자 강제 삭제

ADMIN / SUPER_ADMIN은 일반 회원 계정을 삭제할 수 있다.

SUPER_ADMIN은 삭제할 수 없다.

---

## 6.3 삭제 처리 방식

삭제 시 소프트 삭제 + 익명화를 사용한다.

```text
로그인 불가
이름 → "삭제된 사용자"
로그인 식별자 → 제거 또는 무효화
비밀번호 / 인증정보 → 제거 또는 무효화
과거 참조 → 유지
```

과거 예약, 교환, 공지, 관리자 작업 등의 참조는 유지한다.

화면에는 실명 대신:

```text
삭제된 사용자
```

로 표시한다.

---

# 7. 곡 / 팀 정책

## 7.1 곡 생성 권한

곡 생성 / 수정 / 삭제는 ADMIN / SUPER_ADMIN만 가능하다.

일반 MEMBER 또는 팀장은 곡 구성을 변경할 수 없다.

---

## 7.2 곡 참여자

관리자는 곡마다 참여자를 추가할 수 있다.

예:

```text
장OO  기타
김OO  보컬
이OO  베이스
박OO  드럼
```

참여자 추가 버튼을 제공한다.

---

## 7.3 세션

참여자마다 세션을 입력한다.

예:

```text
보컬
기타
베이스
드럼
키보드
신디사이저
기타 직접입력
```

같은 세션의 참여자가 여러 명이어도 허용한다.

예:

```text
장OO  기타
김OO  기타
```

---
## 7.4 팀장

곡마다 팀장은 정확히 1명.

ADMIN / SUPER_ADMIN은 팀장을 언제든 변경할 수 있다.

팀장 변경 시:

- 기존 팀장 → 해당 팀 관리 권한 즉시 상실
- 새 팀장 → 해당 팀 관리 권한 즉시 획득
- 기존 예약 → 유지
- 기존 교환 요청 → 팀에 귀속되어 새 팀장이 이어서 관리 가능

---

## 7.5 곡 삭제

곡은 물리 삭제하지 않는다.

```text
ACTIVE
ARCHIVED
```

상태를 사용한다.

ARCHIVED 처리 시:

- 일반 곡 목록에서 숨김
- 새로운 예약 불가
- 팀장 운영 대상에서 제외
- 과거 예약 / 교환 / 합주 이력은 유지
- 관리자는 보관된 곡 조회 가능
- 필요 시 ACTIVE 복구 가능

---

# 8. 동아리방 정책

## 8.1 기본 운영시간과 날짜별 Override

동아리방의 기본 운영시간은:

```text
10:00 ~ 22:00
```

이다.

ADMIN / SUPER_ADMIN은 특정 날짜에 한해 운영시간을 `00:00~24:00` 범위에서 30분 단위로 변경할 수 있다.

예:

```text
2026-08-28
08:30 ~ 23:30
사유: 공연 준비
```

해당 날짜에는 팀장도 변경된 운영시간 안에서 정상적인 선착순 예약을 할 수 있다. 관리자만 사용할 수 있는 별도 시간이 아니다.

운영시간은 기본보다 앞/뒤로 확장하거나 단축할 수 있으며, 관리자는 날짜별 Override를 삭제하여 `10:00~22:00` 기본값으로 복원할 수 있다.

시간 표시는 `00:00`부터 하루 끝 경계인 `24:00`까지 허용하고, 모든 시작/종료 시각은 30분 경계여야 한다.

### 운영시간 단축과 기존 예약

운영시간을 단축하여 기존 ACTIVE 예약의 일부 또는 전부가 새 운영시간 밖으로 나가면 해당 예약 전체를 관리자 강제 취소한다.

```text
기존 운영시간 10:00~22:00
관리자 변경   12:00~20:00

10:00~11:00 예약 → 취소
15:00~16:00 예약 → 유지
21:00~22:00 예약 → 취소
```

운영시간 변경으로 취소된 예약도 슬롯을 반환하고, 해당 곡의 팀장 포함 `song_members` 전원에게 취소 알림을 생성하며 관리자 작업 이력을 남긴다.

기존 예약을 다른 날짜나 시간으로 자동 재배치하지 않는다.

---

## 8.2 사용 불가 시간 예외

관리자는 해당 날짜의 **실제 운영시간 안에서** 사용할 수 없는 시간 구간을 등록한다.

예:

```text
2026-08-28
운영시간 08:30 ~ 23:30

12:00 ~ 13:00
사유: 수업

16:30 ~ 18:00
사유: 장비 점검
```

같은 날짜에 여러 사용 불가 구간을 등록할 수 있다.

등록된 구간을 제외한 나머지 운영시간은 자동으로 예약 가능 시간으로 계산한다.

하루 전체를 사용할 수 없게 하려면 그날의 실제 운영시간 전체를 하나의 사용 불가 구간으로 등록한다.

모든 시작/종료 시각은 30분 경계에 맞아야 하며 서로 겹치는 사용 불가 구간은 허용하지 않는다.

일반 사용자에게도 사용 불가 시간과 사유를 표시한다.

### 기존 예약과 겹치는 사용 불가 시간을 추가할 때

새 사용 불가 구간과 겹치는 ACTIVE 예약만 관리자 강제 취소한다.

```text
새 사용 불가 구간과 겹치는 기존 예약 조회/Lock
→ 겹치는 예약만 관리자 강제 취소
→ 해당 예약이 점유한 슬롯 반환
→ 해당 곡의 팀장 포함 song_members 전원에게 취소 알림 저장
→ 하단 알림 메뉴에 미확인 알림 수 표시
→ 알림 메뉴/창고 진입 시 미확인 숫자는 모두 읽음 처리되어 사라짐
→ 읽은 알림은 창고에 유지하고 사용자가 X를 누른 알림만 숨김
→ 관리자 작업 이력 기록
→ 사용 불가 시간 저장
```

기존 예약을 다른 날짜로 자동 재배치하지 않는다.

# 9. 예약 시간 구조

## 9.1 시간표 최소 단위

DB의 원자 예약 슬롯은 항상 **30분 단위**로 고정하고 하루 전체 `00:00~24:00`를 준비한다.

```text
00:00 ~ 00:30
00:30 ~ 01:00
...
23:00 ~ 23:30
23:30 ~ 24:00
```

하루 원자 슬롯 수:

```text
48개
```

월요일~일요일 한 회차는 기본적으로 `48 × 7 = 336개` 원자 슬롯을 가진다.

실제 예약 가능 여부와 화면 노출 범위는 그 날짜의 운영시간으로 필터링한다. 기본 날짜라면 `10:00~22:00`만 예약 가능하다.

45분 등 30분 단위가 아닌 시간은 지원하지 않는다.

---
## 9.2 최대 예약 가능 시간과 화면 슬롯

관리자는 **1회 최대 예약 가능 시간**을 설정한다.

허용 값:

```text
30분
60분
90분
120분
150분
180분
```

DB의 실제 점유/Lock 단위는 항상 30분 슬롯 그대로 유지한다.

사용자에게 보여주는 **일반 예약 슬롯**은 해당 회차의 최대 예약 시간을 기준으로 연속된 빈 시간을 묶어서 만든다.

예를 들어 하루 전체가 비어 있을 때:

```text
최대 30분  → 일반 예약 슬롯 24개
최대 60분  → 일반 예약 슬롯 12개
최대 90분  → 일반 예약 슬롯 8개
```

설정을 변경해도 기존 30분 DB 슬롯이나 기존 예약은 재생성/삭제하지 않는다.

예:

```text
10:00~11:00 기존 60분 예약
최대 예약 시간을 30분으로 변경
```

이면 30분 기준으로 다시 계산했을 때 해당 예약이 점유한 두 개의 30분 슬롯은 예약 가능 목록에서 제외된다.

---

## 9.3 잔여 슬롯

예약 또는 동아리방 사용 불가 시간 때문에 연속된 빈 구간이 최대 예약 시간으로 정확히 나누어지지 않을 수 있다.

이때 남는 30분 배수의 빈 구간은 **잔여 슬롯**으로 별도 표시하고 예약을 허용한다.

일반 슬롯을 먼저 표시하고 잔여 슬롯은 화면 아래에 별도 영역으로 표시한다.

예:

```text
최대 예약 시간 = 90분
11:00~11:30 기존 예약
```

이면:

```text
10:00~11:00  → 잔여 슬롯 60분
11:00~11:30  → 예약됨
11:30 이후   → 가능한 구간을 90분 일반 슬롯으로 다시 분할
```

즉 최대 예약 시간은 상한이며, 잔여 슬롯에 한해서 그보다 짧은 예약을 허용한다.

연속된 빈 구간마다 그 구간의 시작 시각부터 일반 슬롯을 다시 묶는다.

---

# 10. 동일 팀 복수 예약 정책

`동일 팀 복수 예약 허용 여부`는 예약 회차에 종속되지 않는다.

동아리 전체의 현재 운영 설정으로 관리한다.

```text
allowMultipleReservations
```

관리자는 언제든:

```text
허용
불허
```

를 변경할 수 있다.

---

## 10.1 허용 → 불허 변경

이미 여러 예약을 가진 팀의 기존 예약은 유지한다.

예:

```text
아지랑이

월요일 예약
수요일 예약
```

관리자가 복수 예약을 불허해도:

```text
월요일 예약 → 유지
수요일 예약 → 유지
새로운 3번째 예약 → 불가
```

---

## 10.2 불허의 의미

복수 예약 불허는:

> **같은 팀이 같은 대상 예약 회차에 ACTIVE 예약을 2건 이상 가지도록 새로운 별도 예약을 추가하는 행위를 차단한다.**

현재 회차와 다음 회차가 동시에 예약 가능하더라도 각 회차의 ACTIVE 예약 수는 독립적으로 판단한다.

기존 예약:

- 이동 가능
- 연장 가능
- 단축 가능
- 취소 가능
- 교환 가능

이러한 행위는 해당 회차의 예약 개수를 늘리지 않으므로 허용한다.

---
# 11. 예약 회차

## 11.1 의미

예약 회차는:

> **실제로 합주가 이루어지는 주**

를 뜻한다.

기본 주간 기준:

```text
월요일 ~ 일요일
```

예:

```text
1회차
8/24(월) ~ 8/30(일)

2회차
8/31(월) ~ 9/6(일)
```

---

## 11.2 예약 오픈 시점과 회차 분리

예약 회차와 `예약 오픈 시점`은 별개의 개념이다.

예:

```text
2회차 합주 기간
8/31 ~ 9/6

2회차 예약 오픈
8/29(토) 20:00
```

따라서:

```text
8/29(토)

1회차 → 아직 진행 중
2회차 → 예약 접수 시작
```

이 동시에 발생할 수 있다.

여러 회차가 시스템에서 동시에 유효할 수 있다.

---

## 11.3 회차 자동 준비

관리자가 매주 `다음 회차 생성` 버튼을 반드시 누르는 구조로 만들지 않는다.

시스템이 다음 회차를 자동으로 준비한다.

```text
현재 회차
→ 다음 회차 자동 준비
→ 직전 설정 기본값 상속
→ 관리자가 변경할 것이 있을 때만 수정
→ 예약 오픈 시각 도달
→ 자동 오픈
```

관리자가 아무것도 하지 않아도 다음 예약이 정상 운영되어야 한다.

---

## 11.4 직전 설정 유지

새 회차에 별도 설정이 없으면 직전 설정을 기본값으로 이어받는다.

MVP 최초 실행 시 상속할 이전 회차가 없는 경우의 초기값은 다음과 같다.

```text
동일 팀 복수 예약     불허
기본 예약 오픈       회차 시작 28시간 전
                     (월요일 시작 기준 토요일 20:00)
기본 최대 예약 시간  90분
                     (일반 슬롯은 90분 단위, 잔여 구간은 더 짧게 허용)
```

예:

```text
1회차
예약 오픈: 토요일 20:00
최대 예약 시간: 90분
```

다음 회차:

```text
예약 오픈: 다음 토요일 20:00
최대 예약 시간: 90분
```

관리자가 2회차에서 최대 예약 시간을 60분으로 바꾸면:

```text
1회차  90분
2회차  60분
3회차  60분
4회차  60분
```

처럼 이후 별도 변경 전까지 최신 설정이 기본값이 된다.

---

## 11.5 예약 접수 마감

해당 회차의 예약은:

> **일요일 회차 종료 시각까지**

받는다.

기본 동아리방 종료 시간이 22:00이므로 기본적으로:

```text
일요일 22:00
```

까지 해당 회차 예약이 가능하다.

단, 실제 예약하려는 시간은 아직 지나지 않은 시간이어야 한다.

---

# 12. 선착순 예약

## 12.1 서버 시간 기준

예약 오픈 여부는 사용자 기기 시간이 아니라 서버 시간이 기준이다.

```text
예약 오픈
20:00:00
```

프론트의 카운트다운은 표시용이며 실제 판단은 서버가 한다.

---

## 12.2 동시 예약

같은 시간에 여러 팀이 동시에 요청할 수 있다.

예:

```text
A팀 ─┐
B팀 ─┼→ 같은 18:00 슬롯
C팀 ─┘
```

결과:

```text
A팀 → 성공
B팀 → 실패
C팀 → 실패
```

정확히 하나만 성공해야 한다.

정확성은:

```text
PostgreSQL Transaction
+
DB Lock
```

으로 보장한다.

WebSocket은 선착순 승자를 정하는 데 사용하지 않는다.

# 13. 예약 화면 UX

예약 순서:

```text
1. 팀 선택
2. 날짜 선택
3. 예약 길이 선택
4. 시간 선택
5. 예약 요청
```

---

## 13.1 팀 선택

사용자가 팀장으로 지정된 팀만 표시한다.

---

## 13.2 날짜 선택

월간 캘린더 사용.

- 이전 달 보기
- 다음 달 보기
- 좌우 스와이프
- `<` / `>` 버튼
- 예약 불가 날짜 비활성화
- 동아리방 사용 불가 날짜 표시

---

## 13.3 시간 선택

날짜와 예약 길이를 선택하면 `4. 시간 선택` 영역에서 그날 상태를 다음 순서로 보여준다.

```text
일반 예약 슬롯
→ 잔여 슬롯
→ 예약할 수 없는 시간
```

일반 예약 슬롯은 백엔드의 최대 길이 묶음 자체를 큰 카드로 노출하지 않는다. 사용자가 실제로 선택할 수 있는 30분 경계의 시작 시각을 평평한 목록으로 표시한다.

예: 90분 선택

```text
14:00  ~15:30
14:30  ~16:00
15:00  ~16:30
```

즉 일반 슬롯의 기술적인 그룹과 실제 선택 가능한 시작 시각을 구분한다. 팀장은 기존 예약과 사용 불가 시간을 확인한 뒤 실제 시작 시각을 선택한다.

# 14. 전체 일정 화면 UX

전체 일정:

```text
월간 캘린더
→ 날짜 선택
→ 해당 날짜 시간표
```

캘린더는:

- 좌우 스와이프로 월 이동
- 이전 / 다음 달 버튼 제공

날짜를 선택하면 해당 날짜의 합주 예약 현황을 아래에 표시한다.

# 15. 예약 수정

## 15.1 일정 이동

팀장은 자신의 팀 ACTIVE 예약을 다른 빈 시간으로 이동할 수 있다.

예약 시간을 이동할 때 **기존 예약 길이를 유지한다.**

예:

```text
기존
18:00 ~ 19:30
90분

이동
20:00 ~ 21:30
90분
```

현재 관리자가 최대 예약 가능 시간을 60분으로 낮췄더라도 이미 존재하는 90분 예약은 이동 시 원래 90분 길이를 유지할 수 있다. 최대 예약 시간 변경은 기존 예약을 강제로 축소하지 않는다.

새 위치는 해당 날짜의 실제 운영시간 안이어야 하고, 사용 불가 시간 및 다른 ACTIVE 예약과 겹치면 안 된다.

## 15.2 원자적 변경

기존 예약을 먼저 삭제한 후 새 예약을 생성하지 않는다.

```text
현재 Reservation/Slot Lock
→ 새 시간의 Slot 검증/Lock
→ 성공하면 기존 Slot 해제 + 새 Slot 점유 + Reservation 시간 변경
→ COMMIT
```

새 시간 확보 실패 시 기존 예약은 그대로 유지된다.

예약 이동 후 해당 곡의 팀장 포함 `song_members` 전원에게 `RESERVATION_CHANGED` 알림을 생성한다.

---

# 16. 예약 시간 연장 / 단축

팀장은 자신의 팀 예약을 30분 단위로 앞쪽 또는 뒤쪽에서 변경할 수 있다.

## 16.1 연장

예:

```text
현재 18:00 ~ 19:00

앞쪽 연장 → 17:30 ~ 19:00
뒤쪽 연장 → 18:00 ~ 19:30
```

조건:

- 30분 단위
- 연장 결과가 현재 회차의 최대 예약 가능 시간 이내
- 새로 점유할 모든 30분 슬롯이 비어 있어야 함
- 해당 날짜의 실제 운영시간 범위 준수
- 등록된 사용 불가 시간과 겹치지 않아야 함

## 16.2 단축

예:

```text
현재 18:00 ~ 19:30

뒤쪽 단축 → 18:00 ~ 19:00
앞쪽 단축 → 18:30 ~ 19:30
```

단축 후에도 최소 30분은 남아야 한다.

연장/단축 후 해당 곡의 팀장 포함 `song_members` 전원에게 `RESERVATION_CHANGED` 알림을 생성한다.

---

# 17. 예약 취소

팀장은 자신의 팀 ACTIVE 예약을 취소할 수 있다.

취소 시:

```text
Reservation ACTIVE → CANCELED
→ 점유 Slot 반환
→ 시간표 갱신
→ 해당 곡의 팀장 포함 song_members 전원에게 RESERVATION_CANCELED 알림
```

행동한 팀장 본인도 알림 대상에서 제외하지 않는다.

ADMIN / SUPER_ADMIN은 팀장 동의 없이 예약을 강제 취소할 수 있다.

관리자 강제 취소 시 사유와 관리자 작업 이력을 기록하며, 알림 대상은 일반 취소와 동일하게 해당 곡의 `song_members` 전원이다. 다른 팀/일반 동아리 회원/해당 곡 팀원이 아닌 관리자는 수신하지 않는다.

---
# 18. 일정 교환

## 18.1 일반 팀장 간 교환

흐름:

```text
A팀장
→ B팀 일정 선택
→ 교환 요청
→ B팀장 알림
→ 수락 / 거절
```

수락 시 두 예약을 하나의 Transaction으로 교환한다.

둘 중 하나만 바뀌는 상태는 허용하지 않는다.

---

## 18.2 교환 상태

```text
PENDING
ACCEPTED
REJECTED
CANCELED
EXPIRED
```

### 교환 요청 동시성 / 관리자 검토 정책

- 하나의 예약은 동시에 하나의 `PENDING` 교환 요청에만 참여할 수 있다.
- 해당 예약이 이미 다른 `PENDING` 교환 요청의 요청측 또는 대상측으로 사용 중이면 추가 교환 요청을 생성할 수 없다.
- ADMIN / SUPER_ADMIN은 전체 교환 신청 목록을 조회할 수 있다.
- ADMIN / SUPER_ADMIN은 교환 요청을 허가 또는 반려할 수 있다.
- 교환 요청에 참여 중인 예약이 이동 / 연장 / 단축 / 취소되면 관련 `PENDING` 교환 요청은 즉시 `EXPIRED` 처리한다.
- `EXPIRED` 처리 시 상대 팀장에게 교환 요청 만료 알림을 보낸다.

---

## 18.3 팀 귀속

교환 요청은 특정 개인이 아니라 팀에 귀속한다.

팀장이 변경되어도 새 팀장이 기존 PENDING 요청을 이어서 처리할 수 있다.

---

## 18.4 교환 시 예약 길이

일정 교환 또는 일정 위치 변경 시 각 팀의 **원래 예약 길이를 유지**한다.

예:

```text
A팀
18:00 ~ 19:30
90분

B팀
20:00 ~ 21:00
60분
```

교환 후 각 팀은 자신의 예약 길이를 유지하는 방향으로 처리한다.

단, 교환 대상 위치에서 원래 예약 길이만큼 연속된 공간을 확보할 수 있어야 한다.

# 19. 관리자 강제 일정 조정

ADMIN / SUPER_ADMIN은 팀장이 할 수 있는 예약 편집 기능 전체를 강제로 수행할 수 있으며 추가 운영 권한을 가진다.

가능:

- 팀 대신 일정 직접 생성
- 일정 강제 이동
- 앞쪽 / 뒤쪽 강제 연장
- 앞쪽 / 뒤쪽 강제 단축
- 일정 강제 취소
- 두 팀 일정 직접 교환
- 상대 팀장 승인 없이 교환

강제 이동 / 연장 / 단축 / 취소에는 관리자 사유를 기록하고 `admin_action_logs`에 변경 전후 상태를 남긴다.

관리자는 일반 예약 정책 중 다음을 우회할 수 있다.

- 해당 팀장이 아니어도 일정 조작
- 동일 팀 복수 예약 불허
- 일반 예약 오픈 여부
- 교환 상대 팀장 승인

하지만 관리자도 다음 무결성 규칙은 무시할 수 없다.

- 동아리방 동일 시간 중복 예약
- 해당 날짜의 실제 운영시간 밖 예약
- 동아리방 사용 불가 시간 구간
- 신규 예약 및 연장 결과의 현재 최대 예약 가능 시간 초과
- 30분 단위 규칙

기존 예약 이동은 예약 길이를 유지하므로, 최대 예약 시간이 이후 낮아져 기존 예약 길이가 현재 상한보다 길더라도 이동 자체는 허용한다.

관리자 변경/취소 알림도 해당 곡의 팀장 포함 `song_members` 전원에게만 전송한다.

현재 MVP는 합주실이 하나이므로 별도의 멤버 일정 충돌 검사는 필요하지 않다.

# 20. 멤버 일정 충돌 검사 제외

현재 MVP는 동아리방 하나만 관리한다.

따라서:

```text
같은 시간에 두 팀 예약
```

자체가 불가능하다.

그러므로 여러 곡에 참여하는 한 사람이 동시에 두 합주에 배정되는 상황은 공간 충돌 검사에서 먼저 차단된다.

향후 합주실이 여러 개로 확장될 경우에만 개인 멤버 일정 충돌 검사를 추가한다.

# 37. 핵심 설계 원칙 요약

```text
1. 동아리 운영자가 매주 수동으로 시스템을 유지하지 않아도 돌아가야 한다.

2. 예약 회차와 예약 오픈 시점을 분리한다.

3. DB의 실제 점유/Lock 슬롯은 항상 30분 단위로 고정한다.

4. 관리자가 정하는 것은 '1회 최대 예약 가능 시간'이다.

5. 화면의 일반 예약 슬롯은 최대 예약 시간 단위로 묶고, 남는 빈 구간은 잔여 슬롯으로 별도 제공한다.

6. 설정 변경은 기존 예약과 30분 원자 슬롯을 재생성하지 않으며 기존 예약의 이동/교환은 원래 예약 길이를 유지한다.

7. 동일 팀 복수 예약 허용/불허는 회차와 독립적으로 언제든 변경 가능하다.

8. 정책 변경은 기존 예약을 자동 파괴하지 않는다.

9. 선착순의 정확성은 DB Transaction/Lock이 보장한다.

10. WebSocket은 화면의 실시간성만 담당한다.

11. 관리자는 운영 예외를 처리할 강제 권한을 갖는다.

12. 강제 관리자 작업은 이력으로 남긴다.

13. PWA를 사용하여 iPhone/Galaxy 모두 별도 스토어 비용 없이 사용한다.

14. MVP는 단일 동아리, 단일 동아리방을 기준으로 단순하게 유지한다.
```
